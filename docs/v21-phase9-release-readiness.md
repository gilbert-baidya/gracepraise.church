# V21 Admin Control Center — Phase 9 Release Readiness

Phase 9 is a release-candidate hardening pass. It does not deploy Firebase,
Netlify, DNS, or the public ACTIVE mode. The checked-in runtime remains
`SHADOW`, and this document is intended to be reviewed before any production
setup or staged activation.

## Runtime safety contract

The single code-owned runtime contract is
`shared/website-control-runtime.js`:

- Modes are `DISABLED`, `SHADOW`, and `ACTIVE`.
- The checked-in default is `SHADOW`.
- `KILL_SWITCH` is code-owned, defaults to disabled, and falls back to
  `SHADOW`. It does not read Firestore, Auth, LocalStorage, HTML, or a query
  string.
- The public adapter reads only endpoint/test plumbing from its options object;
  it does not read a mode from HTML, route code, LocalStorage, or a URL.
- The localhost-only Playwright harness can select a mode for emulator tests.
  That hook is ignored on non-local hosts and is not a release setting.

Public delivery is atomic: fetch, validate the exact response envelope and
complete feature map, resolve dependencies, build the intended action, then
apply. Any endpoint, network, JSON, schema, revision, timeout, browser parsing,
or dependency failure leaves the current hardcoded website in place. An
unsupported ACTIVE feature is also a no-op: its existing website behavior is
preserved.

## Admin workflow and readiness

The intended workflow is:

`Save Draft → Readiness Checks → Preview Draft → Compare Draft vs Published → Publish Confirmation → Publish`

Readiness blocks Draft publication for invalid schema, unknown/missing feature
IDs, broken dependencies, missing controlled route roots/scripts, missing
required markers, or an unavailable/stale server revision. It distinguishes
safe checks, warnings, and informational local-health instructions. Unsaved
changes disable Preview and Publish. Trusted Publish returns a new Published
revision and the Admin message does not claim that visitor DOM changed
immediately.

The Admin health panel reports runtime mode, Draft/Published revisions,
five ACTIVE-ready features, 45 Shadow-only features, blocking issues, warnings,
endpoint-health scope, and the latest validation time.

## Caching and propagation

The public Function currently sends browser `max-age=30`, CDN `s-maxage=60`,
and `stale-while-revalidate=300`. Fresh requests should normally reflect a
publish after roughly 30–60 seconds, but a stale response may remain visible
for up to approximately five minutes while revalidation occurs. The Admin must
say this explicitly; it must not promise instant propagation.

## Local tools

The initial baseline tool is server/Admin-SDK-only and defaults to dry-run:

```bash
node tools/initialize-website-control.js --dry-run --project-id grace-and-praise-bangladesh
```

It displays the target project, validates the 50-feature all-LIVE baseline,
and performs no write. Local emulator initialization requires an explicit
emulator project and `FIRESTORE_EMULATOR_HOST`; production writes additionally
require `--write --confirm-production` and refuse to replace existing documents
unless `--replace-existing` is explicitly supplied. No credential is stored in
the repository.

The public endpoint health helper is local/emulator-first:

```bash
npm run test:v21:public-config -- --project-id demo-grace-and-praise-bangladesh
```

It requires HTTP 200, the supported schema, a positive revision, exactly 50
feature entries, valid states, and no Draft/Auth/audit metadata. It does not
mutate data and refuses production endpoints unless explicitly authorized.

## Firebase production checklist — manual only

Do not perform these steps as part of Phase 9. Before a future release:

1. Confirm the Firebase project ID is exactly
   `grace-and-praise-bangladesh` and Firestore is in Native mode.
2. Confirm Email/Password Auth is enabled and the approved Auth domains are
   present.
3. Confirm billing/Blaze requirements for callable Functions are understood.
4. Review and deploy Firestore Rules and indexes from this branch.
5. Review and deploy the `gpbc-v21` Functions code.
6. Create the first trusted Admin Auth user through the approved operational
   channel; do not add a public registration path.
7. Assign `admin: true` with the protected Admin SDK utility, record the UID in
   the operational change log, and require sign-out/sign-in to refresh claims.
8. Verify a non-Admin account is denied by both the UI and callable backend.
9. Run the dry-run baseline tool, review its displayed project, then initialize
   Draft and Published only through an approved, separately authorized write.
10. Run the local/emulator and release-candidate suites before any staged
    public activation.

Initial Admin bootstrap is claim-based: the operator must use the Firebase
Admin SDK utility with a known Auth UID and protected credentials, set only
`{ admin: true }`, then have the user re-authenticate. The browser cannot
self-promote and no credentials belong in this repository.

## Admin subdomain and legacy CMS plan

The repository is a static Netlify site (`publish = "."`). A future
`admin.gracepraise.church` setup should be intentionally mapped to the V21
Admin Control Center, with a reviewed host-level route or a separate Netlify
site whose entry point is `/admin/v21/index.html`. Do not rely on `/` resolving
to the public homepage or accidentally expose the legacy CMS.

Future manual setup must include:

- DNS: a reviewed Netlify-provided target/CNAME for `admin.gracepraise.church`.
- Netlify: domain mapping and a host-specific rewrite/entry-point plan.
- Source: V21 Admin assets under `/admin/v21/`; no overwrite of `/admin/`.
- Firebase: add `admin.gracepraise.church` to Auth Authorized Domains.
- Browser security: preserve `noindex`, exclude Admin from public/service-worker
  caches, and review redirect/return behavior after Firebase Auth sign-in.
- CSP: retain the existing minimum Firebase/Functions origins and verify the
  Admin Auth SDK and callable endpoints from the new origin.

The existing `/admin/` Decap CMS remains a separate legacy route. V21 does not
replace its content collections, Netlify Identity, or Git Gateway. Migration,
if ever approved, must be a separate project with an explicit coexistence or
cutover plan.

## Security, CSP, and CORS

The current Netlify CSP already allows the checked-in Firebase Auth SDK,
Google APIs, and the regional callable/public Function endpoint. Future changes
must be additive and origin-specific; do not broaden `connect-src`, scripts, or
frames with an unrestricted wildcard. Re-check `script-src` if the Admin
subdomain changes the Auth redirect origin.

The public Published endpoint is sanitized to `{ schemaVersion, revision,
features }` and may remain readable cross-origin for the public site. Authenticated
Admin callable operations must remain claim-protected and must not use wildcard
CORS. If an Admin subdomain is introduced, explicitly allow the production
origins `https://gracepraise.church`, `https://www.gracepraise.church` only if
used, and `https://admin.gracepraise.church` where required by the Auth/Function
flow.

## Emergency rollback runbook

1. Configuration rollback: restore the previous Draft revision, review it in
   trusted Preview, then Publish it as a new Published revision. Historical
   snapshots are immutable; do not edit old records.
2. Kill switch: in an urgent code/runtime incident, set the reviewed code-owned
   kill switch to enabled and release the change; it forces the safe `SHADOW`
   fallback without depending on Firebase or the network.
3. Code rollback: if the Netlify release itself is defective, roll back the
   Netlify release to the last known-good code revision. This is distinct from
   configuration rollback and requires a separate deployment approval.

## Release-candidate verification record

The release candidate must cover the full local/emulator workflow:

`Admin Login → change approved feature → Save Draft → Preview → Publish → ACTIVE local adapter → restore previous revision → Publish → restored public state`.

It must also cover the safe multi-feature combination:

`homepage.planVisit=HIDDEN`, `homepage.community=HIDDEN`,
`pages.gallery=COMING_SOON`, `pages.planVisit=LIVE`.

The responsive matrix is 375, 390, 768, 1024, and 1440 pixels; representative
ACTIVE cases are run in Light and Dark themes. Accessibility checks cover focus
order, inert/hidden regions, route-state links, Coming Soon status, preview
banner semantics, and keyboard-safe mobile navigation. Existing public
Chromium regression remains the release gate for homepage, Gallery, Plan Your
Visit, Giving, Prayer, Songbook, Devotions, Ministries, About, navigation,
theme, and footer.
